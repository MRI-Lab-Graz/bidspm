# Roadmap: Fixing Known Problems

Status date: 2026-07-13

This roadmap addresses every problem found in the workflow/usability/GUI
assessment of the BIDSPM Runner. Items are grouped into phases by risk and
dependency, not by area. Each item lists: the problem, the root cause, the fix,
the files involved, effort, and how we know it's done.

## Phase 0 — Correctness & environment (blockers)

These affect whether a run launched from the GUI actually works on a fresh
machine. Do these first.

### 0.1 — Interpreter resolution is fragile (HIGH)

- **Problem:** `PYTHON_EXE = .bidspm/bin/python` is a dead symlink on this host
  (points at `/usr/local/fsl/bin/python`, which does not exist). GUI runs only
  survive because of a silent fallback to ambient `python3`, which is correct
  only by luck (it happens to have the deps installed here).
- **Root cause:** hardcoded relative venv path + `os.path.exists() else 'python3'`
  fallback that hides a broken environment instead of reporting it.
- **Fix:**
  1. Resolve the interpreter through a single helper that checks, in order:
     `$BIDSPM_PYTHON` env var → `.bidspm/bin/python` (if real) → `sys.executable`
     (the interpreter already running the server, which by definition has the
     deps) → `python3` on PATH.
  2. If none has the required deps (`flask`, `jsonschema`, `bsmschema`), fail the
     `/run` request with a clear message: "Python environment not set up — run
     `scripts/setup_env.sh`" rather than launching a doomed subprocess.
  3. Add an import-check that runs at server startup and surfaces in the
     existing pre-flight report (`collect_startup_preflight_checks`).
- **Files:** `bidspm_gui.py` (`PYTHON_EXE`, pre-flight),
  `webapp/web_execution_api.py` (line ~171 resolution + validation).
- **Effort:** M
- **Done when:** deleting/breaking `.bidspm/bin/python` still yields correct runs
  via `sys.executable`, and a genuinely dep-less interpreter produces a clear
  actionable error (not an ImportError deep in a detached log).

### 0.2 — Document/repair the venv bootstrap

- **Problem:** the intended isolated venv (`.bidspm/`) does not exist; there is no
  one-command way to recreate it.
- **Fix:** add `scripts/setup_env.sh` that creates `.bidspm` with
  `python3 -m venv` (or `uv venv`), installs `requirements.txt`, and prints the
  activation path. Reference it from README "Installation".
- **Files:** `scripts/setup_env.sh` (new), `README.md`.
- **Effort:** S
- **Done when:** a fresh clone reaches a working GUI run via documented steps only.

## Phase 1 — State hygiene (data clutter & leaks)

### 1.1 — `config/` accumulates transient run settings (56 files and counting)

- **Problem:** every project-less GUI run writes
  `run_settings_override_*.json` / `run_settings_*.json` into `config/`; nothing
  cleans them up. They sit next to real config (`config_schema.json`).
- **Root cause:** `GLOBAL_CONFIG_DIR` used as the scratch destination for
  per-run settings.
- **Fix:**
  1. Redirect these writes to a dedicated run-scratch dir (e.g.
     `GLOBAL_LOG_DIR/run_configs/` or a temp dir keyed by execution id).
  2. Add cleanup on the same `cleanup_old_executions()` schedule that already
     prunes executions (`MAX_EXECUTIONS`), deleting the matching settings file.
  3. One-time: move existing stray files out of `config/`.
- **Files:** `webapp/web_execution_api.py` (lines ~122–159, cleanup),
  `lib/project_manager.py` (dir helpers).
- **Effort:** M
- **Done when:** running from the GUI creates no new files under `config/`, and
  old run-config files are auto-pruned with their executions.

### 1.2 — Remove the hardcoded single-file `.gitignore` patch

- **Problem:** `.gitignore` contains a specific line
  `config/run_settings_e6e0e559afbd2916.json` — a band-aid from a file that
  leaked into tracking once.
- **Fix:** once 1.1 lands, delete that line; ensure the broader ignore
  (`config/run_settings_*`) or the relocation covers it. Confirm nothing under
  `config/` is git-tracked except real config + schema.
- **Files:** `.gitignore`.
- **Effort:** S
- **Done when:** `git ls-files config/` lists only `config.json`,
  `config_schema.json`, and intentional configs.

### 1.3 — Prune/rotate `error_logs/` and root-level logs

- **Problem:** `error_logs/`, `smooth.log` (289 KB), `server.log`,
  `octave-workspace` live in the repo root and grow unbounded.
- **Fix:** move runtime logs under `logs/`, add rotation or a size cap, and
  ensure all are gitignored. Remove `octave-workspace` from the tree.
- **Files:** logging setup in `lib/core.py` / `lib/utils.py`, `.gitignore`.
- **Effort:** S
- **Done when:** the repo root has no runtime-generated log/state files.

## Phase 2 — Front-end maintainability

### 2.1 — Break up the `analysis.html` monolith (HIGH leverage)

- **Problem:** `templates/analysis.html` is 4,442 lines, of which 3,785 are a
  single inline `<script>`. It is the interactive core and is hard to change
  safely — likely why multiple front-end feature branches are stalled.
- **Fix:**
  1. Extract the inline block into ES modules under `static/js/analysis/`,
     mirroring the existing module pattern (`analysis_*.js` already exist).
  2. Group by concern: form/state, path validation, model workspace, run
     controls, participants modal, stats-coverage modal.
  3. Keep the template to markup + a small bootstrap script that wires modules.
- **Files:** `templates/analysis.html`, new `static/js/analysis/*.js`.
- **Effort:** L (own PR; do incrementally, one concern at a time, testing after
  each extraction).
- **Done when:** `analysis.html` has no large inline script; behavior unchanged
  (validated against the run-through checklist in Phase 4).

### 2.2 — Replace hand-maintained cache-busting version strings

- **Problem:** each `<script src=... v='20260616a'>` is bumped by hand; forgetting
  to bump ships stale JS to users (a suspected cause of the "blank page" issue
  the code already works around).
- **Fix:** generate the version token from file mtime or a build hash via a
  Jinja helper / context processor, so every asset URL busts automatically on
  change.
- **Files:** `bidspm_gui.py` (context processor), `templates/*.html`.
- **Effort:** S
- **Done when:** editing any JS file changes its URL token with no manual edit.

### 2.3 — Fix the dead GitHub link

- **Problem:** footer link text is a GitHub URL but `href="#"`.
- **Fix:** point `href` at the real repository URL; open in a new tab.
- **Files:** `templates/base.html` (~line 125).
- **Effort:** S
- **Done when:** the footer GitHub link navigates to the repo.

## Phase 3 — Usability: guided workflow

### 3.1 — Add a first-run guided flow

- **Problem:** the analysis page opens as a wall of path fields (WD, BIDS,
  Derivatives, fMRIPrep, Models, Space, FWHM, Verbosity) plus many modals. New
  users have no "start here → next → run" path, which undercuts the
  ease-of-use goal.
- **Fix:**
  1. Introduce a lightweight stepper: **1. Folders → 2. Model → 3. Subjects &
     options → 4. Run**, backed by the existing accordion sections (no logic
     rewrite; progressive disclosure over the current form).
  2. Reuse the existing per-section completion scoring
     (`model-editor-progress-bar`) as step-completion indicators.
  3. Fold in the `feature/guided-model-workflow` branch if still relevant.
- **Files:** `templates/analysis.html` (post-2.1), new `static/js/analysis/wizard.js`.
- **Effort:** L
- **Done when:** a user with no prior config can create a project and launch a
  pilot run by following visible steps, without reading the README.

### 3.2 — Surface per-subject run failures in the GUI

- **Problem:** the pipeline continues on non-fatal errors (good), but failures
  like "Subjects failed: 1" currently live only in logs.
- **Fix:** parse the run summary and show a failed-subjects badge/list in the
  run panel, linking to the relevant log lines. The "run issues detection"
  work (commit `02a1c17`) is a starting point — extend it to a persistent,
  visible summary.
- **Files:** `webapp/web_execution_api.py` (summary parse), `templates/analysis.html`.
- **Effort:** M
- **Done when:** a run with a failed subject shows a clear warning + which
  subject(s), without opening the log file.

- **Fix:** a short manual (or Playwright) checklist run before/after the 2.1
  refactor: create project, edit model, validate JSON, check folders, open each

- **Effort:** M
- **Done when:** the checklist passes identically pre- and post-refactor.

## Suggested sequencing

1. **Phase 0** (0.1, 0.2) — unblock correct runs on any machine.
2. **Phase 1** (1.1–1.3) + **4.1** — stop state leaks, add the smoke test net.
3. **Phase 2.3, 2.2** — quick wins (dead link, cache-busting).
4. **Phase 2.1** with **4.2** — the big refactor, incrementally and tested.
5. **Phase 3** — guided flow + failure surfacing, on top of the cleaned front-end.

Phases 0, 1, and the quick wins in 2 are safe, contained, and can ship
immediately. Phases 2.1 and 3 are larger and each deserve their own PR.
